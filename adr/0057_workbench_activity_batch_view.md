# ADR-0057：工作台协作在场的批量读取、编辑字段与看板范围变化提示

状态：Accepted；实现、验证与性能测量以[卡 30A 执行记录](../plans/pc-admin-design-v21/card-30a.md)为准。

日期：2026-11-07（Asia/Shanghai）。本决策前向扩展 WBINT-T39 活动合同（[活动接口](../docs/api/workbench/activity.md)），不改写 T39 历史执行记录与证据；前端展示由后继卡 30B 实现。不授权部署、现场启用 `workbenchActivityEnabled` 或任何 Gate。

## 用户确认的口径（原文）

| 编号 | 口径 |
| --- | --- |
| P1 | 新增**批量**只读接口，一次读取当前屏幕上卡片的在场信息；只返回双方都有权限的事项。 |
| P2 | 「正在查看」和「正在编辑」**都显示**。 |
| P3 | **不做**「在线同事」（不新增工作台级别的登记）。 |
| P4 | 单台服务器部署，继续使用**进程内存**保存租约，不引入 Redis 或数据库。 |
| P5 | **性能必须有保障，实现要简单**：优先复用现有代码，不引入新依赖、新存储、新后台任务。 |

## 不变部分

- `WORKBENCH_ACTIVITY_LIMITS`（租约 15 秒、心跳 5 秒、查看空闲 60 秒、编辑空闲 10 秒、2/4/64/128/16 上限）与 `POST /api/workbench/activity` 登记语义不变。
- 登记仍只来自打开的详情抽屉（P3）；不新增工作台级别登记、不新增定时器、存储、依赖或后台任务（P4/P5）。
- 结果仍不含请求人自己，只含当前双方都获权的同事；不输出 principal_id、browser_id、会话、外部身份或正文。

## A1 人员结构增加编辑字段

`WorkbenchActivityPerson` 为 `{display_name, mode, field, expires_epoch_ms}`。`mode='EDITING'` 时 `field` 为当前编辑的字段（`internal-note | ticket-handling | ticket-completion | manual-review`），否则为 `null`。同一同事有多条租约时合并为一人：任一租约为编辑即为编辑；有多个编辑字段时取 `editedAt` 最近的一个；期限取最大值。编辑空闲 10 秒后按原规则降为查看，`field` 同时变为 `null`。

排序：**编辑者在前**，同类按显示名 `localeCompare` 排序；最多 16 人不变。单张接口与批量接口使用同一人员结构。

字段名是 T39 原合同明确不输出的内容；本 ADR 依据 P2 前向开放「字段种类」这一项，仍不输出字段正文、草稿或任何内部标识。字段本身已经经过原字段写权限重验（`authorize(…, field)`）才可能成为 EDITING。

## A2 批量读取接口

`POST /api/workbench/activity/batch-view`，与活动命令同一 HTTP 模块，复用 Cookie 身份、同源 Origin、`x-csrf-token`、无 query、32KiB 正文、功能开关与安全错误处理。

- 请求 `{schema_version:1, targets: WorkbenchActivityTarget[]}`：1–100 个，每个 kind/id 校验与单张接口一致；按规范化后的 `kind:id` 去重并保留请求顺序。0 个或超过 100 个返回 400。
- 响应 `{schema_version:1, items: {kind, id, people}[]}`：只包含 `people` 非空的目标，按请求顺序。

实现（性能关键）：

1. 校验后执行原有的过期清理，再对当前租约（≤128）做一次遍历，得到「持有非请求人租约」的目标集合；这是请求内的临时 Set，不跨请求保存。
2. 不在该集合中的目标直接跳过，**不做任何鉴权调用**。
3. 只对集合中的目标逐个调用原单张 `view()`（复用，不复制）；某目标返回 401/403/404 只跳过该目标，其它错误仍使整个请求失败（不吞存储故障）。
4. 不缓存跨请求结果，不新增常驻数据结构。

### 最坏情况开销

设请求中持有他人租约的不同目标数为 T，这些目标上的租约数为 L：

- 需要鉴权的目标数 T ≤ min(请求目标数 100, 有租约的不同目标数 ≤ 128)，即单次请求最多 100 个目标进入 `view()`；
- 每个目标的 `authorize` 调用 = 请求人 2 次（读取前与读取后的围栏复核）+ 该目标每条租约 1 次，因此总调用数 ≤ 2T + L ≤ 2×100 + 128 = 328；
- 无人目标的开销仅为一次 ≤128 条的内存遍历，不触发鉴权。

## A3 看板范围变化提示

原 `signature()` 只对当前账号自己登记过的事项计算投影签名，他人在其它事项上的在场变化不会提示看板。现在活动模块维护一个**进程内整数版本号**，在以下情况 +1：新增租约、删除租约（释放、按认证释放、关闭、失权移除）、查看/编辑切换、编辑字段变化、过期清理。普通心跳续租不变更版本号。`signature()` 返回「版本号 + 原自身事项签名」的组合，因此任何在场变化都会让每个连接的签名改变。

SSE 发送循环：

- 租约变化沿原 `wakeup` 唤醒 SSE（原有路径）；
- 连接建立后的首次签名只作为基线，不发送提示；
- **同一连接 1 秒内最多发送一次** `workbench.activity.changed`。节流在原发送循环内判断；被节流的变化保留旧签名，由下一次已有的 wakeup 或 recovery 轮询（默认 5 秒）补发，不新增定时器；
- 提示仍只有 `data: {"schema_version":1}`，无 id，不进入 Event Log/replay/cursor。

隐私：提示从「自己可见事项的投影变化」放宽为「某处在场有变化」。它只泄露进程内某个活动租约发生了变化这一事实与时间，不泄露人、事项、字段或数量；接收方仍须通过批量/单张接口在双方权限下读取。看板对没有自身租约的连接计算签名时不调用鉴权（只读版本号）。

## 回退

删除 `POST /api/workbench/activity/batch-view` 与版本号前缀（`signature()` 恢复只返回自身签名、SSE 去掉首次基线与节流判断）即可恢复原行为；`field` 为向后兼容新增字段，前端解析同时接受旧三键结构。默认 `workbenchActivityEnabled=false` 时以上全部不可用，与原合同一致。无数据库、迁移或持久状态需要回滚。

## 性能目标与实测

A5 目标与实测见[卡 30A 执行记录](../plans/pc-admin-design-v21/card-30a.md#a5-性能测量)。其中「100 个目标中 64 个有人，p95 < 100ms」在本地真实 PG 鉴权下**未达到**：每个有人目标约需 3 次真实 `authorize`（每次含主体、会话与事项读权限查询）。按 P5 不引入缓存；可选的后继方向记录在执行记录中，需另行决策。
