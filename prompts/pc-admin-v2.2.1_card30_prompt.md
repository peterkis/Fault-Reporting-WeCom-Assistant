## 一、背景与用户确认的口径

现有实现（WBINT-T38 / T39，`app/server/src/workbench-activity.mts`、`features/activity/*`）：

- 只有打开详情抽屉时才登记「我在看」：租约 15 秒、心跳 5 秒；查看空闲 60 秒、编辑空闲 10 秒失效；在内部备注、处理记录、完成记录、人工复核输入时为「编辑」。
- 读取只有单张接口 `GET /api/workbench/items/{kind}/{id}/activity`，结果不含自己、只含双方都有权限的同事；人员只有 `display_name`、`mode`、`expires_epoch_ms`，**没有正在编辑的字段**。
- SSE 只发一个不带内容的 `workbench.activity.changed` 提示，而且 `signature()` 只覆盖**当前账号自己登记过的事项**，所以别人在看其它卡片时，看板这边收不到任何变化。
- 界面上只有抽屉里一行纯文字「X正在查看」。

**用户确认的口径**：

| 编号 | 口径 |
| --- | --- |
| P1 | 新增**批量**只读接口，一次读取当前屏幕上卡片的在场信息；只返回双方都有权限的事项。 |
| P2 | 「正在查看」和「正在编辑」**都显示**。 |
| P3 | **不做**「在线同事」（不新增工作台级别的登记）。 |
| P4 | 单台服务器部署，继续使用**进程内存**保存租约，不引入 Redis 或数据库。 |
| P5 | **性能必须有保障，实现要简单**：优先复用现有代码，不引入新依赖、新存储、新后台任务。 |

原型依据：**01e 工作台 · 协作在场**（主要依据），01 看板、01c 列表中的示例卡片。

## 四、卡 30A · 后端（现在开始）

- 分支：`codex/v221-card30a`；执行记录：`plans/pc-admin-design-v21/card-30a.md`；新建 `adr/0057_workbench_activity_batch_view.md`。

### A1 人员增加正在编辑的字段

- `WorkbenchActivityPerson` 增加 `field: WorkbenchActivityField | null`（`mode = 'EDITING'` 时为当前编辑的字段，否则为 `null`）。数据已在租约中，只需在 `view()` 合并同一同事多条租约时带出：同一人有多个编辑字段时取最近一次编辑的字段。
- 人员排序改为：**编辑者在前**，同类按显示名排序。
- 单张接口与批量接口使用同一个人员结构；同 PR 更新契约与 `features/activity/client.ts` 的解析（只放宽为接受 `field`，其余校验保持）。

### A2 批量读取接口

- 新增 `POST /api/workbench/activity/batch-view`（与现有 activity 路由同一个 HTTP 模块，复用相同的鉴权、CSRF、开关与错误处理）。
- 请求：`{schema_version: 1, targets: WorkbenchActivityTarget[]}`，`targets` 1–100 个、去重、kind / id 校验与单张接口一致；超过 100 返回 400。
- 响应：`{schema_version: 1, items: {kind, id, people: WorkbenchActivityPerson[]}[]}`，**只返回有人的目标**（没人的不出现在结果里）。
- 实现要求（性能关键，P5）：
  1. 先在内存里把当前租约按 `targetKey` 分组（一次遍历，租约总数上限 128）；
  2. 请求中**没有任何其他人租约**的目标直接跳过，**不做任何鉴权调用**；
  3. 只对「有其他人租约」的目标调用现有的单张 `view()` 逻辑（复用，不复制一份），逐个处理；某个目标鉴权返回 401 / 403 / 404 时只跳过该目标，不让整个请求失败；
  4. 不缓存跨请求结果，不新增数据结构。
- 在 ADR 中写明：最坏情况下一次请求的鉴权次数上限（= 有租约的不同目标数，≤ 128）。

### A3 看板范围的变化提示

- 现状：`signature()` 只计算当前账号自己登记过的事项，别人的在场变化不会提示到看板。
- 修改（最简单的方式）：在 activity 模块内维护一个**整数版本号**，在以下情况 +1：新增或删除租约、模式在查看 / 编辑之间切换、编辑字段变化、租约过期被清理、按认证释放。`signature()` 返回值改为「版本号」与原有自身事项签名的组合，这样任何在场变化都会让每个连接收到一次 `workbench.activity.changed`。
- 确认租约变化会唤醒 SSE 发送循环；**服务端合并提示**：同一个连接 1 秒内最多发送一次 `workbench.activity.changed`（在现有发送循环里做节流，不新增定时器）。
- 提示仍不带任何内容（只有 `schema_version`），在 ADR 中说明这只泄露「某处在场有变化」，不泄露人和事项。

### A4 契约与 ADR

- 更新 `contracts/workbench_activity_contracts.d.ts`、对应 JSON Schema、`docs/api/*`；新建 ADR-0057：P1–P5 原文、A1–A3 设计、最坏情况开销、隐私说明、回退方式（删除批量接口与版本号即可恢复原行为）。

### A5 性能测量（必须提供）

在测试中构造最坏情况：128 条租约（分布在 64 个目标上）、64 个 SSE 连接、批量请求 100 个目标，记录：

| 指标 | 要求 |
| --- | --- |
| 批量请求（100 个目标中 0 个有人）耗时 | 不调用鉴权；p95 < 5ms |
| 批量请求（100 个目标中 64 个有人）耗时 | p95 < 100ms（本地测试库） |
| 一次租约变化触发的 SSE 提示数量 | 每个连接 ≤ 1 次 / 秒 |
| 内存 | 不新增与目标数量相关的常驻结构 |

如果某项达不到，停下来在执行记录中说明原因和建议，不要引入缓存或新依赖。

## 五、卡 30B · 前端（30A 与卡 29 都合并后开始）

- 分支：`codex/v221-card30b`；执行记录：`plans/pc-admin-design-v21/card-30b.md`；截图：`docs/ui/evidence/v221-card30b/`。
- 可修改：`features/activity/*`、新建 `design/components/PresenceStack/*`、`design/components/TicketCard/*`（只限在场展示）、列表视图「问题」单元格、`app/WorkbenchDetail.tsx`（只限在场胶囊与字段提示）、相关测试与 fixture。不可修改：后端、契约、看板与列表的其它结构。

### B1 在场头像组件 `PresenceStack`

- 输入：人员数组（已按编辑者在前排序）、尺寸（16 或 18）。
- 规格（原型 01e 图例）：
  - 头像沿用 `Avatar`，相邻重叠 4px，每个头像外有 2px 白色间隔；
  - 正在查看：外圈 1.5px 品牌蓝（`--brand`）；
  - 正在编辑：外圈 1.5px 橙色（`--tone-attention-fg` 或最接近的现有 Token），右下角 11px 圆形橙色角标内含 7px 白色铅笔图标；
  - 最多显示 2 个，超出显示「+N」（11px `--text-secondary`）；
  - `role="img"`，`aria-label` 为「周宁正在编辑内部备注、沈然正在查看」。
- 悬停 300ms 后显示深色提示（沿用现有 Tooltip）：每人一行「头像 16 + 姓名 + 正在查看 / 正在编辑{字段名}」。字段名：internal-note → 内部备注，ticket-handling → 处理记录，ticket-completion → 完成记录，manual-review → 人工复核。
- 出现 / 消失只做 150ms 淡入淡出，不改变所在行的高度和布局（预留宽度不够时组件绝对定位在原位置左侧，不挤压热度标签）。

### B2 看板卡片

- 头像组放在卡片编号行右侧、热度标签左侧，间距 8px，尺寸 18。
- 不改变卡片的描边、热度色环和选中样式。
- **未领取且有人在看**的卡片：悬停卡片时，卡片下方（或卡片内底部）显示蓝色提示条「{姓名}正在查看这张工单，领取前可先确认」（12px，`--tone-brand-subtle` 底、`--brand` 文字、眼睛图标）；有人在编辑时文案为「{姓名}正在处理这张工单」。不阻止领取。
- 已关闭卡片不显示在场。

### B3 列表行

- 头像组放在「问题」单元格最右侧（标题与标签之后，`margin-left: auto`），尺寸 16；不影响标题省略规则（标题仍优先被省略）。

### B4 抽屉

- 用抽屉顶栏右侧的「在场胶囊」替代正文里的纯文字（`data-workbench-activity` 保留在胶囊上）：`--bg-subtle` 底、圆角 13、高 26，内容为 18px 头像组 +「N 人在看」（12px `--text-secondary`）。没人时不显示。
- 同事正在编辑**当前可见的同一个字段**时（`field` 与输入区的 `data-activity-field` 相同），在该输入区顶部显示橙色提示条：铅笔图标 +「{姓名}正在编辑{字段名}，同时编辑可能互相覆盖」（12px，`--tone-attention-bg` 底、`--tone-attention-fg` 文字）。**不锁定输入**，不改提交逻辑。

### B5 读取与刷新（性能关键，P5）

- 新建在场存储：`Map<targetKey, people>`，用 `useSyncExternalStore` 按 key 订阅，**每张卡片只订阅自己的 key**，在场变化只重新渲染受影响的卡片，不触发整个看板或列表重新渲染。
- 读取时机：
  1. 首次进入工作台、切换看板 / 列表、筛选或翻页导致**已渲染卡片集合**变化时：防抖 500ms 后批量读取；
  2. 收到 `workbench.activity.changed`：防抖 1s（合并多次提示）后批量读取；
  3. 只读取**当前已渲染**的卡片（折叠分组中的不读），每次最多 100 个，超出时只取前 100 个（按渲染顺序）。
- 过期：根据每个人的 `expires_epoch_ms` 在前端隐藏已过期的人，使用**一个**全局 5 秒定时器统一检查（只有在场存储非空时运行，空时停止）。
- 工作台不可见（`document.hidden` 或桌面端 `isWorkbenchVisible()` 为假）、离线、实时连接断开、`activity_enabled` 为假时：清空存储，不发请求；恢复后立即读取一次。
- 复用现有 `captureWorkbenchRead`、鉴权与错误处理；请求失败静默处理（不弹提示），下次触发时重试。
- 抽屉内的单张读取保持现状（继续由现有 `ActivityPeople` 逻辑负责登记与读取），只换展示。

### B6 性能验收（必须提供）

- 渲染测量：看板 60 张卡、其中 1 张的在场变化 → 只有这 1 张卡片组件重新渲染（用 React Profiler 或渲染计数断言）。
- 网络测量：10 秒内连续 20 次 `workbench.activity.changed` 提示 → 批量请求 ≤ 10 次（防抖生效）。
- 空闲测量：没人在场时，60 秒内除心跳外没有批量请求、没有运行中的 5 秒定时器。
