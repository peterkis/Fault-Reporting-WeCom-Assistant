## 2. 高风险项

### R01 企业微信能力与文档不一致

通过 G0 实测群聊、媒体、主动发送、卡片、重连和单活；不采用 Windows RPA 替代可靠接入。

### R02 公网 Pilot 数据安全

截图可能包含患者信息。Phase 1/2 必须明确数据驻留、加密、访问、审计、备份、留存和删除；未经审批不得发送公网模型。

### R03 Pilot Ticket Core 过度扩张

Pilot 只实现试点闭环和迁移所需能力，不建设完整医院ITSM，不提前引入资产、BPM或复杂基础设施。

### R04 Phase 1 偷渡医院依赖

不得通过共享数据库、内网临时接口、医院 SSO 或院内 Outbox 绕过边界。Phase 1 所有必需能力必须在 Pilot 内独立降级。

### R05 漏单、重复单和虚假状态

依靠数据库幂等、先保存后回复、Action状态机、事件和Outbox同事务；不得依赖进程内或Redis唯一状态。

### R06 群消息噪声与敏感信息扩散

默认只处理明确发给机器人；群内只发首次确认和公共信息，个人进度优先单聊。

### R07 AI/OCR 排队或越界

AI异步、限流、可关闭、无生产写权限；关键临床、权限、数据和安全类别始终人工控制。

### R08 Incident 错误关联

默认人工确认，支持解除并保留独立Intake；禁止仅按类别和时间自动并单。

### R09 Phase 3 映射与双事实源

Ticket编号、状态、人员、附件、事件和通知语义可能不一致。必须先盘点真实契约，再通过Adapter、映射表、批次迁移和对账切换。

### R10 切换与回滚期间双写

必须明确每个切换状态的写入所有权、通知所有权和回滚规则。不得使用无边界双向同步长期过渡。

### R11 文档基线再次漂移

架构变化必须更新 `docs/architecture_baseline_status.md`、ADR、路线图和Backlog；已废弃材料不得重新进入实施Prompt。

## 3. 开放问题

### Gate 0

1. 群内必须 @ 还是能收到普通文本？
2. 图片/mixed 的真实 Frame、大小和下载时效？
3. 主动群消息、单聊和卡片的显示/提醒效果？
4. 一个 Bot 多实例连接的实际限制？
5. 锁定哪个 SDK 版本和包哈希？

### Phase 1

6. 公网 Pilot 的域名、证书、服务器、数据库和备份责任人？
7. Pilot 处理人员如何认证，最小角色和处理组如何维护？
8. H5 网络路径是否可用；不可用时的最小处理入口？
9. 临时回执文案、自动关闭24h/48h和非工作时段规则？
10. 试点群、试点科室、服务时间和退出机制？
11. Phase 1 截图是否只登记待补传，还是允许受控存储？

### Phase 2

12. 私有对象存储、病毒扫描和截图留存周期？
13. AI服务器CPU、内存和虚拟化超售情况？
14. 评估集的数据使用和安全审批？
15. Incident自动化是否始终保持关闭，何时允许评审？

### Phase 3

16. Hospital Tickets 的权威API、状态机和版本并发语义？
17. 身份、科室、院区和处理组的权威来源？
18. 附件和内部/外部备注如何映射？
19. 通知由Pilot还是医院平台承担，切换点是什么？
20. 历史Pilot数据迁移范围、切换窗口、回滚授权和归档期限？

## 4. 决策管理

- 开放问题形成结论后更新文档、Backlog和相关配置；
- 核心变化新增或取代ADR；
- 记录日期、决策人、替代方案、风险和回滚影响；
- 不允许只在聊天、代码注释或临时环境变量中冻结架构决策。
