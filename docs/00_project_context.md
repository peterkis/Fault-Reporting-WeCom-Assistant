# 00. 项目背景与医院上下文 V1.4

## 1. 当前事实

医院主要通过企业微信群进行信息故障报修，存在漏看、无回执、状态不透明、数据无法统计和公共故障重复沟通等问题。报修群约有 800 名临床成员，项目目标包括 10 秒内真实确认、完整留痕、进度透明、可靠通知和月度统计。

当前项目已完成 Phase 1 收口，并在逐任务独立授权下推进 Phase 2：

- Gate 0 已完成企业微信真实能力验证；
- P1-001 至 P1-011 已完成既定本机验收；
- P1-012 已完成真实测试群 E2E，并于 2026-08-30 获项目负责人正式 Go 批准；
- Phase 1 状态为 `DONE / GO`；
- Phase 2 状态为 `IN_PROGRESS`，P2-A 的 P2-001、P2-002 与随后独立授权的 P2-003 均已完成；当前无活动任务或 Lane，下一任务候选 P2-004 未授权，P2-G1 为 `NOT_STARTED`，全部 P3 任务未启动；
- 所有 P2/P3 Feature Flag 保持 `false`，本授权不等同于生产上线、临床上线或 AI 自动回复批准；
- 没有历史业务 Ticket；
- 没有需要兼容、迁移或退役的旧工单系统。

## 2. 阶段边界

### P1

纯外网企业微信试点，零医院内网依赖；现已完成并取得 `GO`。该结论不是生产或临床上线批准。

### P2

P2-001 的 Conversation Thread、Session、Conversation Item 与控制模式契约已冻结；P2-002 已在现有 Unified Ticket Core 上完成持久、可重建 Timeline 投影。当前无活动任务；人工工作台、多轮 AI、媒体/OCR、Incident 和运营能力仍须逐任务另行获批，不得提前组装 P2-G1。

### P3

接入未来新建的医院内网报修门户、医院 API、监控告警和身份组织能力。P3 不承担历史数据兼容。

## 3. 医院能力候选

进入 P3 前再确认：

- 医院 SSO；
- 人员、任职、科室、院区和处理组数据；
- 医院 API 平台；
- 新内网报修门户；
- 监控告警来源；
- 内网到云端的主动出站 Connector 网络路径。

这些都不是 P1 的可用依赖。

## 4. 核心业务目标

- 建立统一、可信的信息故障服务入口；
- 明确每个状态的真实语义；
- 让临床不用反复催问；
- 让信息科获得结构化服务数据；
- 支持公共故障统一处置；
- 形成服务目录和故障知识资产；
- 企业微信和未来内网入口共享同一 Unified Ticket。

## 5. 数据和算力约束

- 截图可能含患者敏感信息；
- 外部模型前必须脱敏和审批；
- 核心链路必须在无 GPU 条件下运行；
- 云服务器为 2 核 4GB；
- AI 是可关闭增强；
- 不引入 Kafka、Kubernetes、重型多平台客服栈作为上线前置。

## 6. 非目标

- 电话与语音通话报修；
- 全院群无感监听；
- 多医院法人多租户；
- AI 自动执行生产运维命令；
- 完整 IT 资产管理；
- 历史 Ticket 兼容或导入；
- 双工单系统切换；
- 未经验证的全自动 Incident 合并。
