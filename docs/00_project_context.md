# 00. 项目背景与医院上下文

## 1. 项目背景

医院当前主要通过企业微信群进行信息故障报修。该方式符合临床人员即时沟通习惯，但缺少稳定的服务受理和工单闭环：

- 临床人员无法确认信息科是否已经看到消息；
- 报修依赖人工盯群，存在漏看、迟看和重复催问；
- 处理过程缺少结构化记录；
- 无法稳定统计故障类别、响应时间、处理时间和科室分布；
- 同一公共故障会被多个科室重复报告，信息科需要反复解释；
- 信息科已投入处理工作，但临床难以感知过程和价值。

原始方案指出报修群约有 800 名临床成员，核心目标包括 10 秒内确认、报修留痕、进度透明、月度统计和纯 CPU 运行。

## 2. 医院现有能力

以下内容来自本项目讨论背景，进入开发前由项目负责人最终确认：

### 2.1 现有平台

- 医院已有自研 API 平台，承担院内系统调用和接口聚合；
- 已有 Tickets 工单系统或相关工单模块；
- 已有 Hub、Outbox/Relay、SSE 和内部消息能力；
- 已有统一身份认证接口，可返回用户名、姓名、科室和角色；
- 已有 PostgreSQL、Redis、MinIO 或同类基础设施；
- Web 技术体系以 Next.js、React、Node.js/Express 为主；
- 信息科开发和运维人力约 1—2 人，应保持架构轻量。

### 2.2 组织范围

- 项目服务于同一医院法人下的多院区体系；
- 本期不建设多个医院之间的多租户隔离；
- 从第一版保留 `campus_id`、`department_id`、`ward_id`、`location_id` 等多院区字段；
- 申报人所属科室、故障发生科室和实际受影响科室必须分开。

### 2.3 数据和算力约束

- 故障截图可能包含患者姓名、住院号、医嘱、检验结果等敏感信息；
- 消息、截图、OCR 和模型推理不得上传到未经批准的公网模型；
- 前期无 GPU，核心业务必须在纯 CPU 条件下可运行；
- AI 是增强能力，不能影响核心报修链路；
- 医院内网和企业微信之间采用 WebSocket 出站长连接，不依赖公网入站回调作为主方案。

## 3. 核心业务问题

### 3.1 响应无感知

临床人员发送消息后，没有可靠、及时的系统确认。“信息科可能已经看到”不能替代明确服务回执。

### 3.2 状态黑盒

临床无法区分：

- 消息已被看到；
- 工单已生成；
- 已进入处理池；
- 已有人接单；
- 正在处理；
- 等待补充；
- 已处理待确认；
- 已关闭。

如果系统在无人接单时直接回复“正在处理”，会形成新的不真实感知。

### 3.3 报修无结构化留痕

微信群消息不等于工单记录。需要保存：

- 原始消息；
- 申报人；
- 群或单聊；
- 院区、科室、位置；
- 图片和错误代码；
- 工单状态时间线；
- 通知送达记录；
- AI 建议及人工修正；
- 公共故障关联。

### 3.4 公共故障重复报修

公共故障不是“同类别工单”。同一时间的 HIS 登录失败和 HIS 打印失败可能属于不同问题。必须保留每位申报人的独立记录，并由 Incident 关联同一公共事件。

### 3.5 临床沟通噪声

800 人群不适合广播每张工单的每次状态变化。应采用：

- 群内：首次确认、公共故障公告、必要的公共进展；
- 单聊：接单、待补充、处理结果、恢复确认；
- 信息科内部：Hub、灵动岛、派单工作台。

## 4. 项目目标

### 4.1 产品目标

- 建立统一、可信的信息故障服务入口；
- 明确每个状态的真实语义；
- 让临床不用反复催问；
- 让信息科获得结构化服务数据；
- 支持公共故障统一处置；
- 逐步形成服务目录和故障知识资产。

### 4.2 技术目标

- WebSocket 连接稳定、可监控、可重连；
- 消息不丢、不重复；
- 工单状态与通知一致；
- AI 关闭时核心链路继续运行；
- 对附件、患者信息和 Secrets 进行最小化处理；
- 适合 1—2 人维护，不引入非必要复杂基础设施。

## 5. 本期非目标

- 电话和语音通话报修；
- 全院所有企业微信群无感监听；
- 多医院法人多租户；
- AI 自动执行生产运维操作；
- 完整 IT 资产管理；
- 全自动知识库问答；
- 强制所有工单上传处理照片；
- Kubernetes、Kafka、复杂多 Agent 编排；
- 未经验证的全自动公共故障合并。

## 6. 术语

| 术语 | 定义 |
|---|---|
| Channel Message | 企业微信传入的一条原始消息 |
| Service Intake | 一次完整的服务受理，可包含多条文字和图片 |
| Ticket | 处理团队需要完成的工作任务 |
| Incident | 多个申报共同对应的公共故障 |
| Reporter Subscription | 某个申报人对工单或公共事件的通知订阅 |
| Notification Outbox | 与业务事务同时写入的待发送通知事件 |
| AI Decision | AI/OCR 产生的结构化建议和审计记录 |
| Resolver Team | 负责处理某类服务的团队 |
