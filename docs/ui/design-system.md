## v2.2.0 关闭 / 恢复 / 列表收尾（卡29，前向覆盖 v2.1.9 同项）

原型依据：[v2.2.2 原型](prototype/医小修%20PC%20管理端%20v2.2.2%20设计原型.html) 01d（主要），01b、01c 继续有效。

- **对话框统一规格**：关闭事项宽 440、恢复事项宽 400；圆角 14（`--radius-lg` + `--space-0-5`）、内边距 20、标题 16 / 600、右上关闭按钮；第二行「编号 · 标题」13px `--text-secondary`。原因单选行高 36，选中行 `--brand-subtle` 底。
- **二级原因子选项**：「非 IT 范围」只保留 3 个具体情况，沿用原因码、只改显示名：业务咨询（`BUSINESS_CONSULTATION_CONFIRMED`）、其他部门职责（`OUT_OF_SCOPE_CONFIRMED`）、服务请求（`SERVICE_REQUEST_CONFIRMED`），各带 12px `--text-tertiary` 辅助说明。紧贴父选项下方缩进 26px，`--bg-subtle` 底、圆角 8，标题「具体情况 *」；子选项行高 32、13px，选中白底 + 1px `--border-brand-subtle`。关闭命令（工单与受理事项）后端校验同步收紧为这 3 个码；人工复核工作区自身的 8 个原因不变。关闭记录、卡片 / 列表原因标签使用新显示名，历史上的其它码保留其记录名称。
- **原单组合框**：一个输入框，前缀 14px 搜索图标，输入即搜索（防抖 250ms，复用可见工单搜索）；下拉行高 40：「20px 分类图块 + 编号（`--font-mono` 12px）+ 标题单行省略 + 阶段标签」；上下键选择、Enter 确认、Esc 关闭；无结果「没有找到可关联的工单」。选中后框内「工单图标 + 编号 + 标题 + 24px 清除按钮」。只显示 `IT-` 对外编号，不能选自己。
- **通知与终止提示**：通知块只讲通知（「将通知报修人」+ 文案 /「不会通知报修人」）；「其他」为复选框「通知报修人」，勾选显示文案、不勾选显示「不会通知报修人」。「进行中的跟进与提醒将一并终止」在通知块外单独一行（13px `TriangleAlert` + 12px `--tone-attention-fg`），只在处理中 / 等待类关闭时出现。删除「关闭后不计入完成数…」。
- **底栏**：一行，左侧「✓ 草稿已保存 · 清空」（12px `--text-tertiary`，「清空」为 ghost 小按钮），右侧「取消」+ 主按钮；无草稿不显示左侧。不出现只有图标没有文字的状态。
- **⋯ 菜单**：宽 220、圆角 10、内边距 4；菜单项行高 32、14px 图标 + 13px 文字、左对齐；「刷新可用操作」（`RefreshCw`）为普通项；分隔线后「关闭事项…」为危险项（`CircleX`、`--tone-danger-fg`，悬停 `--tone-danger-bg`）。
- **恢复确认**：信息块（`--bg-subtle`、圆角 8、内边距 10 12）三行「标签 56px + 值」：回到（阶段标签）、负责人（头像 20 + 姓名 / 未领取）、通知（「关闭时已通知，将通知报修人已重新受理」/「关闭时未通知报修人，本次不发送」/「关闭通知尚未送达，恢复后将按送达结果决定是否通知」）。信息块下 12px `--text-tertiary`「已终止的跟进与提醒不会自动重建，需要时请重新发起。」，与信息块间距固定，不用负外边距。主按钮「↶ 确认恢复」。
- **抽屉已关闭态**：标题下灰色「⊗ 已关闭」徽标，不显示绿色「已处理」与子状态。下一步卡中性灰（`--bg-subtle` + 发丝描边），28px 白底圆内 16px `CircleX`，第一行 12px「已关闭 · 不计入完成数」，第二行 14px / 600 原因（如「非 IT 范围 · 业务咨询」「重复报修 · IT-…」），右侧 secondary「↶ 恢复」。恢复只从下一步卡进入；事项已不再关闭但仍有未核对的恢复操作时，「核对恢复」保留在关闭记录中。
- **关闭记录**：一个「关闭记录」分节，按时间倒序，每次关闭一条：「头像 20 + **姓名** + 人工关闭 / 系统判定 · 时间」；下一行原因标签 + 原单链接（有才显示）+「已通知报修人」（有才显示）；说明为下方 `--bg-subtle` 小块；恢复为该条下 12px「↶ 姓名 恢复 · 时间」。空值字段不显示。
- **提示条**：关闭成功「已关闭」+「可在「已处理 · 已关闭」中恢复」；恢复成功「已恢复」+「已回到{列名}」。其它功能的「原操作已核对为提交…」本卡不改。
- **「已取消」→「已关闭」**：PC 端状态映射、动态记录、标签中 `CANCELLED` 显示「已关闭」，状态值不变。搜索「细分状态」里 `CLOSED` 与之同名，显示为「已关闭（已完成）」以区分。
- **看板重复标签**：「重复 · IT-…」在同一个标签内，编号 `--font-mono` 12px。
- **列表缺失值**：报修人与位置只缺一项时只显示存在的一项，都缺时显示「—」；负责人单行省略，`title` 为全名，行高 44；阶段分组行白底（含悬停），只有子分组行 `--bg-subtle`；「收起」与「显示剩余 N 项」同样式并带 14px `ChevronUp`。搜索结果与看板卡片带相同的分类与时效只读字段。

## v2.1.9 统一关闭与恢复（卡27C-B，前向覆盖关闭停止项）

依据原型 01b 与 ADR-0056；用户另行明确授权最小后端读取补充、Workbench 已关闭卡片接线及本节规范。原命令、权限、内部说明隔离、UNKNOWN 原 UUID 核对保持。

- 「关闭事项」覆盖所有当前可关闭 Ticket 和待判断 Intake；三工作台角色可见，只读账号不显示。关闭对话框 440px、圆角14px、内边距20px，沿现有间距/圆角 Token 组合；六原因单选行36px，选中使用 brand-subtle。非 IT 范围展开原八项二级原因；重复原单选填，通过授权搜索选取编号与标题；OTHER 必填内部说明，通知复选默认关闭。
- 通知块使用 bg-subtle、Bell 与服务端固定矩阵文案；内部说明永不拼入提示。进行中额外提示“进行中的跟进与提醒将一并终止”。末行 tertiary 固定提示“不计入完成数，可在已关闭中恢复到关闭前所在列”。提交中及结果未知时禁止新提交。
- 恢复使用 ghost / Undo2；看板和列表悬停、键盘焦点进入时可见，触屏始终可见。卡片详情链接、恢复按钮、原单按钮是独立控件，禁止交互元素嵌套在详情链接内。列表恢复位于负责人单元格，沿既有行级命中层次。
- 恢复确认从只读历史接口读取有效恢复列/负责人及实际送达状态；原负责人失效回待接单/未领取，SENT 才提示重新受理通知，UNKNOWN 明示待核实。成功后在目标列使用 brand-subtle 淡出1.2秒；减少动态效果时同样短暂保留静态底色。
- 关闭通知在恢复弹层打开后仍可能送达。恢复提交前重读最新历史；通知事实或恢复目标变化时更新提示并要求再次确认，不发送本次恢复命令。未送达时的提示说明后续送达仍可能触发恢复通知，不把一次读取当作锁内最终事实。
- 原因标签使用 reason_label；非 IT 范围附二级原因，重复且有关联显示“重复 · 原单编号”。超长省略、title全文；原单按当前授权搜索精确编号后打开抽屉。抽屉记录显示操作人、时间、来源、原因/二级、原单、内部说明与实际通知状态；历次关闭/恢复按版本及时间倒序，分页读取，缺失事实不推断。
- 加载更早关闭记录失败时保留已成功读取的页面并允许重试；当前 READ/会话失效时立即遮蔽资料，沿既有授权清理缓存。

## 卡27B B5日期组合扩展（2026-11-06，前向覆盖本卡原停止项）

用户在首轮本地交付后授权补齐后端、合同及接口文档，支持结束方式与今天／近两天／近7天／本月／自定义／全部日期组合。沿既有BoardDatePresets、日期选择器和FilterChip，不增加依赖、Token、业务命令或权限。

- 今天／近7天／本月继续解析为北京时间的明确起止自然日，与手填日期同用 `range=custom&closed_from=YYYY-MM-DD&closed_to=YYYY-MM-DD`；包含结束日，后端使用次日零时的半开上界。非custom不携带日期字段。
- 列表结束方式在所有有效日期范围均可操作；搜索／结束方式生效时仍显示同一日期控件。切换日期、结束方式、看板／列表及详情返回保留其余已提交条件，清分页游标；结束搜索保留当前有效日期及范围，不留下缺失边界的custom。
- 日期和结束方式属于视图条件，更新它们不得抹掉搜索框中尚未提交的文字或其它条件草稿。原选择器、可见焦点、导航阻塞、失权清理与命令恢复保持。
- 日期、结束方式或scope条件切换开始时即锁定其提交入口，直到目标URL提交且该次搜索settle；期间禁用日期、结束方式、scope、刷新及搜索提交/结束，q草稿保持可编辑。使用原禁用态，不增加Token/视觉模式，也不把此读取忙碌态接入核心回复或命令就绪屏障。切看板/列表仍保留目标条件，不能困住忙碌锁；不通过提高服务端限额或固定等待规避并发读取。
- 筛选继续由后端在READ和LIMIT之前执行，日期及结束方式参与原游标身份。不得把已加载页在客户端再筛选当作完整日期查询。未知关闭时间仍只在全部日期出现，RESOLVED原待确认语义保持。

## v2.1.7 已处理分组（卡27B，前向覆盖同项旧规格）

以用户提供的 v2.2 原型 01、01b、01c 为视觉依据，读取事实沿 [ADR-0055](../../adr/0055_workbench_closure_kind_projection.md)，执行与停止项见[卡27B](../../plans/pc-admin-design-v21/card-27b.md)。本节只调整读取与展示，不新增关闭原因、状态转换或恢复命令。

- 第三列仍为「已处理」，分为「已完成」「已关闭」，列头为两组计数之和。普通看板使用当前日期范围的服务端 `group_counts`；搜索或仅筛已加载事项时明确计数范围，不将已加载条数冒充服务端总量。两个组均复用第一列的折叠样式：fs-xs / fw-medium / text-secondary 与折叠箭头；已完成默认展开、已关闭默认折叠，后者右侧以 text-tertiary 显示「不计入完成数」。会话级偏好按当前账号保存，不存业务资料。各组的「显示剩余 N 项」只计本组已加载但折叠的卡片，位于本组末尾；服务端下一页仍是独立动作。
- 日期预设与自定义范围同时作用于两组，删除原 `cancelled` 专用范围。CANCELLED 与 DUPLICATE_LINKED / IGNORED 统一进入已关闭；日期未知不根据 updated_at 推断，仅在全部日期中显示。
- 已关闭卡片使用 bg-subtle、1px / 6% 中性描边，不显示热度和色环；分类瓷砖 grayscale(1)、opacity .55。编号 text-tertiary，右上 CircleX 为 fs-xs 对应12px，时间沿 `formatListTime` 后接「关闭」；缺失时间明确「时间未记录」。标题 fs-md / fw-medium / text-secondary，无删除线。底部左侧中性原因标签使用 `reason_label`，有原单时追加「 · 编号」，编号 font-mono；右侧人工来源显示头像及「姓名 · 人工关闭」，系统来源显示 Bot 及「系统判定」，未知来源只显示已知姓名。S3 停止时不显示恢复入口。
- 抽屉「关闭记录」只读当前详情的 closure，展示操作人、时间、方式、原因、原单和说明。缺失事实标明未记录或未关联，不从标题、自由文本或其他事项猜测。
- 「今日完成」只计算 closure.kind=COMPLETED，且 completed_at 为当前上海日期且不晚于当前时刻；DISMISSED 的重复、取消、系统不受理均不计入。汇总仍保留已有「已加载范围」说明。
- 已关闭分组不注册放置目标，位于第三列完成放置区以外；拖到第三列的完成区继续打开既有合法表单，不直接写入。拖到已关闭区域不得触发业务请求。
- 列表工具栏增加「结束方式：全部 / 已完成 / 已关闭」FilterChip，沿现有搜索调用 `closure_kind`，可与全部日期预设及自定义范围组合；已关闭行使用 text-secondary，原因列最大宽度由现有间距Token组合为160px。筛选值参与原游标身份，切换时清旧游标，不放宽 READ 或权限。

## 结论

页面难看的根因不是「Airbnb + Notion」这个方向错了，而是**没有一个被代码强制执行的设计系统**：v1.0 规范只覆盖了看板、列表、抽屉三屏，之后每个功能（会话、通知异常、新报修、附件、语音、处理记录、设置……）都在各自的 CSS 里自己定颜色、字号、圆角；10-28 引入 HeroUI 后又叠加了第二套 Token。结果是三套视觉语言同时在屏幕上说话。

本规范（v2.0）给出的决策：

1. **一个底层语法**：以 Notion 的「工具型密度 + 中性灰阶 + 发丝线」为骨架；Airbnb 只贡献「温度、单一品牌色、浮层质感、友好文案」四样东西，且只出现在规定位置。
2. **一套 Token、三层结构**：原始值 → 语义 Token → 组件 Token；HeroUI 的 `--accent / --border / --surface` 全部由语义 Token 派生，功能 CSS 禁止写裸值。
3. **一套页面模板**：所有一级页面共用同一个 PageHeader + Toolbar + Content 骨架，宽度、标题、间距不再按页面各写一份。
4. **一张状态语义表**：状态只在一个地方定义颜色，来源/渠道一律中性灰，人名永远不做成彩色标签。v2.1 类别瓷砖按第四章采用服务目录大类色。
5. **用 lint 守住**：Stylelint 禁裸 hex / 裸 px 字号 / 未定义变量，CI 卡死，否则三个月后会再次漂移。

### 1.2 视觉层：截图里直接看得见的问题

**团队工作台（看板）**

- **标题区过重**：64px 图标瓷砖 + 36px/700 标题 + 句式副标题，占了首屏约 15% 高度，是营销页写法，不是工作台写法。「人工协作」徽标孤零零挂在右侧。
- **内容居中留白不对**：1240px 容器在 1920 屏上居中，左侧留出大片空白，而会话页又是左对齐铺满——两页切换时标题位置跳动。
- **状态表达了三次**：列头有黄色「待受理」胶囊 + 整列米黄底色 + 卡片内又有黄色「待接单」标签。三列底色（米黄/淡蓝/淡绿）使整板发花。
- **标签语义不清**：一张卡可同时出现 待接单(黄)、H5报修(灰)、本轮已催单(橙)、补充待跟进(橙、还换行)。「已领取」与「待接单」同色、却表示不同阶段。
- **卡片内部节奏乱**：编号(等宽 12) → 标题(15/600) → 报修人·科室(13) → 标签行 → 底部处理人+时间；处理人「冯刚」与报修人「冯刚」重复出现且样式不同，没有超时信息。
- **工具栏两行断裂**：第一行页签 + 按钮组，第二行「已加载 8 项」+ 日期筛选；「应用 / 清除」两个按钮形态不同。

**工单详情抽屉**

- **主操作色源不对**：「登记完工」是硬编码 `#315fed` 亮蓝，全站其他地方没有这个蓝。
- **「派单」按钮悬空**：右下单独一行，与顶部操作区割裂。
- **区块标题无层级**：报修描述 / 报修资料 / 报修人通知 / 处理记录 全是 14/600，而「处理与协作」又是灰色折叠文字，读不出它们是同级。
- **人名做成彩色标签**：处理记录里「冯刚」是青色胶囊、「系统」是黄色胶囊，与状态标签长得一样，读者会把人当成状态。「内部」又是带描边的第三种标签样式。
- **通知时间线孤立**：一个蓝点 + 文字堆叠，没有与下方处理记录共用时间线组件。

**会话页**

- 标题无图标瓷砖、左对齐，与工作台模板不同；副标题与分割线紧贴，没有留白。
- 搜索标签在上、输入框在下、「搜索」按钮另起，三个元素高度不同；两个下拉框带外置标签，而工作台的日期筛选是行内标签——同一类控件两种写法。
- 空状态提示「当前筛选没有获权联系人」被挤到列表底部，与右侧大空状态各说各话；分页按钮在没有数据时仍占位。
- 右侧 1300px 宽的空白只放了一个小图标 + 两行字，句子在「责」处断行。

### 1.3 根因归纳

1. **规范覆盖面太窄**：v1.0 只定义了 3 个屏幕，没有定义表单、筛选、空状态、弹窗、时间线、媒体、分栏布局等「通用积木」，新功能只能自己发明。
2. **两套 Token 并行**：HeroUI 接入时只覆盖了部分变量，按钮、字段圆角（5px）与自建的 6px 不同，主色变成近黑。
3. **没有组件层**：标签、区块标题、字段行、空状态都是每个 feature 用 class 自己拼，而不是 `<Tag tone>` / `<Section>` / `<EmptyState>` 这样的共享组件。
4. **风格融合发生在组件级而非层级**：Airbnb 的大标题、大瓷砖、色块列与 Notion 的小字号、发丝线、灰按钮逐个组件混搭，形成「大头小身」。下一章解决这一点。
5. **没有自动化约束**：库里有 CI 门禁，但没有任何样式层面的检查，Agent 生成代码时自然就会写裸值。

## 二、方向：Airbnb × Notion 按「层」融合，而不是按「组件」混搭

两者的设计目标不同：Airbnb 是消费级、低频、以图片和转化为中心；Notion 是生产力、高频、以文字和密度为中心。信息科工程师一天盯着工作台几小时，**骨架必须是 Notion**；Airbnb 只用来提供「人情味」和「精致度」，并且被限定在以下层。

| 层 | 来源 | 具体做法 | 不要的做法 |
| --- | --- | --- | --- |
| 信息密度与布局 | Notion | 14px 正文、32px 控件高、浅灰侧栏、属性表、发丝线分隔、整宽工作区 | Airbnb 的大留白、居中窄容器、36px 大标题 |
| 中性色 | Notion 暖灰 | 全站只用一组暖灰（`#37352F` 系），不再混入 Tailwind 冷灰 `#64748b/#e5e7eb` | 两套灰混用 |
| 品牌色 | Airbnb 方法论 | **一个**自信的品牌色（医小修蓝 `#2563C9`），只用于：每屏唯一的主按钮、当前选中、链接、未读点 | 照搬 Airbnb 玫红：在医院语境里红色留给「危险/超时」 |

| 媒体 | Airbnb | 附件图片网格 8px 圆角、统一比例裁切、悬停微放大 | 不同尺寸描边盒 |

## 三、设计原则（按优先级）

用词：**MUST** 必须；**SHOULD** 默认应当，偏离需写理由；**MUST NOT** 禁止。

1. **一屏一个主操作**（MUST）：品牌蓝实心按钮每个可见区域（页面、抽屉、弹窗）最多 1 个。工作台是「新报修」，抽屉是当前状态下的下一步（领取 / 开始处理 / 登记完工）。
2. **颜色承载明确的信息**（MUST）：v2.1 分为阶段 / 紧急 / 类别 / 人四层，颜色面积与信息重要程度成正比；来源、渠道、科室、人名文字保持中性。类别只用统一瓷砖，人物色只用于已有稳定哈希头像；品牌操作色沿既有规范。
3. **同一信息只表达一次**（MUST）：看板列已表明阶段，卡片内不再重复阶段标签，只显示「阶段内子状态」（如已领取）。
4. **层级靠字重与灰度，不靠字号堆叠**（MUST）：字重只有 400/500/600 三档；字号只有 6 档（见 Token）。
5. **容器隐形**（SHOULD）：分区优先用间距，其次发丝线，最后才是背景色块；禁止嵌套盒子（框内再加框）。
6. **同类事物同一样子**（MUST）：所有页面用同一个 PageHeader；所有筛选用同一个 FilterBar；所有时间线用同一个 Timeline。
7. **不只靠颜色**（MUST）：超时/异常必须同时有文字或图标；文字对比度 ≥ 4.5:1。
8. **温度只在边界上**（SHOULD）：弹层、图片、空状态、成功反馈可以柔和友好；主工作区保持安静。

`src/design/heat.ts` 唯一导出阈值常量 `HEAT_THRESHOLDS_MINUTES = [5, 20, 60, 240]`。`heatOf(startIso, nowMs)` 为纯函数，不读取系统时钟：

| 时长区间 | tone / label | ring |
| --- | --- | --- |
| < 5 分钟 | null | — |
| 5–20 分钟（不含 20） | neutral / N 分钟 | null |
| 20–60 分钟（不含 60） | warning / N 分钟 | null |
| 60–240 分钟（不含 240） | attention / N 小时 | attention |
| ≥ 240 分钟 | danger / 超时 N 小时 | danger |

分钟与小时均向下取整；缺失、无效或未来起点、非有限 nowMs 返回 null。ring 是语义键 `null / 'attention' / 'danger'`，由共享组件引用对应 `--ring-*`。输入必须为带时区的 ISO 时间，避免浏览器本地时区改变热度。热度起点由 `cardHeatStart` 统一选择：待处理用 `created_at`，处理中用 `stage_entered_at`（为空则无热度，不回退到 `created_at` 或 `updated_at`），已完成无热度。`cardHeat(item, now)` 统一将 API 上海民用时间转换为带 `+08:00` 的 ISO 时间后调用 `heatOf`；看板、详情、会话关联卡及「已超时」计数/红点/筛选使用这一函数。非 ticket 事项也显示热度，红色超时卡均计入；计数范围仍是已加载数据。

### 4.4 层级与动效

- z-index：sticky 10 → dropdown 40 → drawer 50 → modal 60 → toast 70 → tooltip 80，禁止其它数字。
- 时长：fast 120ms（悬停、按下）、base 180ms（展开、弹层）、slow 240ms（抽屉、弹窗）。缓动 `cubic-bezier(.2,0,0,1)`，退出 `cubic-bezier(.4,0,1,1)`。
- 抽屉从右侧 16px 位移 + 淡入；弹窗 0.98→1 缩放 + 淡入；卡片悬停只变阴影不位移。尊重 `prefers-reduced-motion`。

### 4.5 焦点规则（修订 10-29 版本）

10-29 的「全站去掉焦点环」解决了鼠标点击出现黑框的问题，但也让键盘用户看不到当前位置。v2.0 规则：鼠标交互不显示焦点环（保持现状）；仅 `:focus-visible` 显示 `0 0 0 2px var(--border-focus)`，输入框聚焦用 1px `--border-focus` 描边 + 白底。

## 五、布局与页面模板

### 6.13 头像 Avatar

圆形；一般尺寸20/24/32，消息组专用28（avatar-msg）；一般字号为尺寸50%、500，28px消息头像固定fs-xs/500；四种柔和色按 `personId ?? name` 的完整原始输入稳定哈希；系统事件用 `--bg-muted` 底 + 图标；未派单用 1.5px 虚线圆。

显示字由 `Avatar/avatarInitial.ts` 的纯函数 `avatarInitial(name)` 统一计算：先 `trim()`，循环剥离末尾全角/半角括号后缀（`/\s*[（(][^（）()]*[）)]\s*$/u`）；剥离后为空则取原名第一个非括号、非空白字符，仍为空返回「—」。以拉丁字母开头则取首字母大写，否则用 `Array.from` 取最后一个 Unicode 字符。例：张三（合成）→三，Peter→P，（合成）→合。`aria-label` 和 `title` 保留完整原名，颜色哈希输入不随后缀剥离改变。

`--fs-avatar-sm: calc(var(--avatar-sm) / 2)`（20px 头像内为 10px）是头像字形专用 Token，不扩展正文六档字号。

### 6.14 v2.1 卡 8 收尾

- 顶栏在所有一级页面常显面包屑，包括工作台与新报修；右侧仅连接状态与设置入口。连接状态使用现有 `RealtimeView.status`，中性文字，不把连接情况当作业务就绪或送达事实。
- 姓名下显示「部门 · 人工协作 / 只读」，沿用现有展示判定；无部门资料时仅显示角色。窄屏保留原账号菜单的退出与设置能力，以设置图标进入；不扩大任何权限。
- 列尾只保留 ghost「显示剩余 N 项 / 收起」；`N` 是已加载但折叠的条数。「已加载 N 项」放列尾原生 tooltip；服务端「加载下一页」仍单独保留，不冒充剩余总数。
- 通知异常刷新放 PageHeader 右侧 ghost 图标按钮；无数据时不显示分页说明与下一页。副标题为「发送失败或结果待核对的通知。查看不会触发重发。」。
- 工单备注的原刷新按钮移入既有「⋯」，名称为「刷新可用操作」，原读取、阻塞与失权清理不变。工单空态统一「这里暂时没有工单」；具体已处理时间范围保持原提示。

本节依据 [v2.1 方案](design-system-v2.1.md) §4.1、§4.2、§4.4、§4.5；其余色彩、热度、类别及下一步卡随各自任务卡实施。

## 九、工程约束、落地路线与验收

### 9.1 目录与导入顺序

```text
app/pc-admin/src/design/
  tokens.css            第 1–3 层 Token + 旧变量兼容层（本规范附件）
  base.css              reset、排版、焦点规则（替代 heroui-workbench.css 的焦点部分）
  status-map.ts         第七章状态 → tone 映射
  components/           Button Tag StatusBadge SourceLabel Avatar PageHeader Toolbar
                        FilterSelect SearchField Section PropertyList Timeline
                        EmptyState InlineAlert Drawer Modal TicketCard BoardColumn
features/*/             只组合 design/components，原则上不再有自己的 .css
```

导入顺序：`tailwindcss` → `@heroui/styles` → `design/tokens.css` → `design/base.css` → `design/components/*.css` → 极少量 `features/*.css`。

实际入口由 `main.tsx` 最先导入 `design/fonts.css`，再导入 `design/foundation.css`，该文件按上述顺序用 CSS `@import` 接入 Tailwind、HeroUI 与 Token，再加载其余样式。不要在 TypeScript 中直接副作用导入 `@heroui/styles`：包根会解析为 JavaScript 工具导出；显式 `/css` 出口也缺少本项目严格副作用导入所需的类型声明。CSS 入口复用现有构建机制，无需增加声明豁免。

文件位置：`tokens.css` → `app/pc-admin/src/design/tokens.css`；`.stylelintrc.json` → `app/pc-admin/.stylelintrc.json`（与该应用的 package.json 同级，在 `app/pc-admin` 下运行 `npx stylelint "src/**/*.css"`）；本规范导出 Markdown → `docs/ui/design-system.md`。当前代码在该配置下的基线违规为 600 条。

### 9.2 自动化约束（接入现有 gate）

- **Stylelint**：`features/**/*.css` 与 `src/style.css` 禁止裸 hex/rgb、禁止 `font-size`/`border-radius`/`box-shadow`/`z-index` 使用非 `var(--*)` 值、禁止 `!important`、禁止 rem。仅 `design/tokens.css` 豁免。
- **未定义变量检查**：脚本扫描所有 `var(--x)`，不在 tokens.css 或 HeroUI 变量清单内即失败（当前会报 7 个）。
- **JSX 检查**：ESLint `no-restricted-syntax` 禁止在 features 中直接写 HeroUI `<Button variant=…>`、`style={{color…}}`、`className` 含 `status-chip`。
- **主按钮计数**：现有 Playwright 截图用例中加一条断言：每个 page / dialog / drawer 内 `[data-tone=primary]` ≤ 1。
- **AGENTS.md**：增加一条「UI 修改先读 `docs/ui/design-system.md`，只用 design/components；新增视觉模式先改规范再写代码」。

### 9.3 落地顺序（不改业务合同，每步独立可发布）

1. **Token 底座**：接入 tokens.css；全量替换 `var(--fw-medium)`→`var(--fw-semibold)`；删除 `heroui-workbench.css` 中的色值定义。此步视觉变化很小，主要消除两套 Token。
2. **全局替换裸值**：按映射表把 136 个 hex、19 种字号、22 种圆角收敛到 Token；开启 Stylelint（先 warning，清零后改 error）。
3. **骨架组件**：PageHeader / Toolbar / EmptyState / Button 封装，所有一级页面切换。这一步解决「页面之间不一致」。
4. **信息组件**：Tag / StatusBadge / SourceLabel / status-map；重做 TicketCard 与 BoardColumn。这一步解决「看板花」。
5. **抽屉**：Section / PropertyList / Timeline；操作区收拢；通知并入时间线。
6. **会话与其它页面**：Split 模板、会话列表项、消息气泡；通知异常、来源群、新报修切换到 Table / Form 模板。
7. **清理**：删除兼容变量层与废弃 class；`style.css` 目标 < 150 行。

2026-11-01 卡 1 执行确认：直接采用 v2 字号和尺寸，接受本卡因 Token 接入产生的排版及布局变化，替代原任务卡“无布局变化”的验收限制。旧变量兼容层补齐到本章已有语义值；旧 10/14/18/28px 间距分别向上归到 12/16/20/32px，不保留旧字号、控件或头像尺寸。列底统一 `--bg-subtle`，四组旧头像色复用既有 info / attention / review / warning 的底色与前景色。现有表格 900px 横向滚动下界和标题图标容器暂保留，随后续 Table / PageHeader 模板卡迁移；本卡不提前重写页面结构或业务交互。
