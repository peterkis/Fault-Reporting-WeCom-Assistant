# PC 管理端 Web 工作台设计

状态：REVIEW DRAFT，已确认业务决定与待整体确认的页面建议分别标注。日期：2026-09-23。

本文记录 grill-with-docs 讨论中已确认的需求和待决事项；不是最终设计冻结或运行验收。用户已授权进入合成数据视觉原型阶段。既有业务规则以 AGENTS.md、架构基线及 Accepted ADR 为准。领域术语见 [CONTEXT.md](../../CONTEXT.md)，目标与现状差异见 [领域设计](../domain-modeling/domain-design.md) 和 [探索记录](../domain-modeling/exploration.md)。原型入口与运行说明见 [原型说明](../../web/admin-workbench-prototype/README.md)。

## 1. 已确认的产品边界

- 首先打磨 PC 管理端 Web；完成后以 Tauri 2 提供桌面宿主体验。桌面登录、原生通知、升级等细节留待后续设计。
- 同事普遍可以沟通协调，多数亲自接单，少数把工单派给其他同事或其他人员，日常没有明确岗位分工。
- 共用一套工作台，按授权执行操作。日常兼任不代表自动授予全部管理权限。
- 首页默认显示团队工作的卡片看板，三列为“待受理 → 处理中 → 已关闭”。顶部提供“团队工作／与我有关”范围切换及“看板／列表”展示切换。需跟进、有新补充的卡片突出显示。
- 设计覆盖实际需要的完整流程，不限于现有界面换肤；新增服务端能力需在实施拆分时明确列出。
- 通过 SSE 提供查看/编辑协作提示，不因打开或编辑而自动锁单；持久处理责任与实时活动分别展示。冲突提交明确提示并保留输入。活动提示的触发与失效细节待定。
- 每日新增通常几十单，不超过 100 单；同时在线通常 3–4 人，最多 10 人；主要屏幕 1920 × 1080。
- 同时未完成工单规模尚未给出，不能从每日新增量推定。
- 首版提供工作人员“新建报修”，支持电话、现场等代录场景；区分实际报修人与代录人，提交到待受理或选择由本人处理。不伪装成报修人亲自在企业微信提交。
- 代录优先搜索并选择经核实的企业微信成员；查不到时允许填写姓名、科室及联系方式并标记身份待核实，不阻止受理。故障描述必填，位置允许明确选择“不清楚”；不按同名自动绑定。目录搜索是否可用须验证当前应用的权限及接口。
- 代录选择到已核实且可接收应用消息的成员时，通过医小修应用发送进展及完工通知；仅有手填资料且身份待核实时，由工作人员线下联系并显示“需人工联系”，不猜测收件人。代录来源仍保持真实，不伪装为成员自主网页提交。

## 2. 已确认的体验问题

1. 人工复核与后续处理需要跨多个标签切换，任务上下文不连贯。
2. 操作按钮、状态选择和逐步确认繁琐，不符合实际处理直觉。
3. 各类工单状态不直观；未处理、待跟进、超时以及需要本人行动的事项不突出。
4. 报修人补充材料后，工作人员不能及时获知。
5. 多人协作时，无法明确判断谁在处理哪张工单。

后续以这些场景检验页面方案，而非仅验证颜色和布局。

### 拖动选型建议与验证边界

用户确认采用 GitHub 开源拖动库，要求自然、流畅且与 HeroUI 协同。当前建议首选 [dnd-kit](https://github.com/clauderic/dnd-kit) 的 React 适配层：支持多容器、可定制外观、指针及键盘输入、拖动浮层。2026-09-23 npm 查询 `@dnd-kit/react` 为 0.5.0，peerDependencies 接受 React/React DOM 18 或 19。该新接口与旧 `@dnd-kit/core` 文档不可混用。版本仅为研究快照，未安装或锁定。

备选 [Pragmatic drag and drop](https://atlassian.design/components/pragmatic-drag-and-drop/about) 提供框架无关、无样式的拖动基础，但辅助操作与视觉反馈仍须集成。选择 dnd-kit 是针对本项目自定义卡片、浮层与键盘交互的工程建议，不是已完成 HeroUI 联调的结论。

建议将拖动行为放在卡片外层与专用拖动手柄，HeroUI 负责卡片内容、菜单和表单，Motion 负责面板等其他动效，不让两个库同时控制同一元素的位移。实施时验证菜单/按钮不误触拖动、焦点恢复、键盘拖动、滚动边缘、长列表、新 SSE 事件、取消与提交冲突。流畅度必须通过实际卡片负载下的浏览器测试和性能录制验证；不预先宣称无冲突或不卡顿。

## 5. 设计必须保留的业务区别

- 会话沟通责任与工单处理责任是两份独立事实，可由同一人承担。
- 服务受理、人工复核与工单不能因统一呈现而被合并为同一业务对象。
- 工单状态只能通过合法业务动作改变；看板分组不创建新状态。
- 内部备注与报修人可见内容保持明确受众边界。
- 通知发送结果与工单处理结果独立。
- 公共故障恢复不能隐式关闭个人工单。
- 实时查看/编辑提示不能直接成为工单责任或修改授权。

## 6. 已确认的操作与协作规则

- 普通故障卡片及待复核报修提供“我来处理”，明确操作者为处理人并进入处理中；无需逐项接单、确认、开始、再确认。保留次级选项“先接单，稍后处理”。这是目标业务行为，现有服务端是否支持完整复合命令须在实施前落实。
- 复核和后续处理保持同一操作上下文；减少界面步骤不绕过必要的材料校验、权限、版本及业务动作记录。
- 普通操作不弹重复确认；处理人填写处理过程描述后直接关闭工单，不要求报修人逐单确认。取消等影响较大的动作保留确认或原因。关闭依据记为工作人员完工关闭，不能伪造报修人恢复确认；见 [ADR-0024](../../adr/0024_staff_completion_and_takeover.md)。
- 所有已获工作台业务访问授权的内部同事都可以相互接管、转派和代办；最后接管者承担当前工单处理责任。该业务授权不扩大为系统管理、审计或通知核对权限。
- 默认接管工单并承接其关联服务会话的沟通责任，可明确保留原沟通人；没有关联会话的网页报修不伪造会话。代办关闭提供“接管并关闭”的一次提交。复合责任变更必须原子完成，不能先后部分成功。
- 保留完整服务接管链：首次接单、每次转派和接管、前后责任人、操作人、发生时间及所属处理轮次可追溯；当前负责人变化不能覆盖既往记录。
- 完工表单分为必填的内部“处理过程”和明确对外可见的简短“告知报修人的结果”；允许主动复制内部过程后编辑对外摘要，不默认外发内部过程。
- 完工通知中的入口进入医小修本人报修处理详情。原报修人在详情点击“仍未解决”，重开同一工单并回到待受理列，突出提醒上一轮处理人；其他同事仍可接管。普通补充、致谢不自动重开，新故障另建报修。入口链接不代替本人认证与归属校验，重复点击不能产生多个重开轮次。
- 用户确认继续保留 ADR-0023 来源策略：Bot 来源个人通知走 Bot 私聊，医小修网页来源走应用消息，群来源另有独立来源群提醒。个人完工通知提供医小修本人详情入口，不因统一详情入口改写来源。当前源码覆盖与现场部署状态分别核验，不据目标体验宣称已实现。
- 有工作台账号的同事可按权限承接。外部厂商或维修人员不能登录，其处理事项的内部工单责任归派发坐席，不因交给外部人员而消失。
- 个人未读与团队待跟进独立：同事看过不消除负责人的个人未读；仅打开详情不代表已响应。
- 回复成功只解除本次针对的补充待跟进；发送失败或结果未知继续提示。普通内部备注不自动解除，可选择“记录处置并标记已跟进”或明确标记已跟进。操作期间新到达的补充继续提醒，不能被旧操作清除。发送成功按可核验的渠道回执表达，不冒充报修人已读。
- 尚无人领取的报修有新补充时，在团队看板突出显示，直到有人承接跟进。承接本身不代替明确处置，个人未读与团队待跟进仍独立。
- 展示每个流转环节的真实等待时长，支持下次跟进时间。仅有明确时限的事项标超时；阈值、工作时间口径及提醒策略暂未确定。

## 6.1 已确认的看板、卡片与详情

| 看板列 | 展示范围 |
| --- | --- |
| 待受理 | 待人工判断、未接单、已领取未开始、重开待重新处理 |
| 处理中 | 正在处理、等待报修人、等待厂商 |
| 已关闭 | 已确认关闭、按批准规则关闭，以及仍处于已解决待确认的记录 |

已解决待确认在“已关闭”列展示时仍标明其真实细分状态，不因归组改写数据库状态或冒充已确认关闭。新目标流程由处理人填处理过程后直接关闭，不再常规停留等待报修人确认。取消工单默认从主看板移出，通过筛选查看。关联同一受理/工单的复核信息整合展示，不能制造重复工单卡片。

- 卡片默认显示问题标题、故障位置、报修人、细分状态、新补充/待跟进提示、处理人、当前环节时长；设置后显示下次跟进时间。工单编号弱化，实时活动头像按需显示，优先级有依据时显示。
- 长报修内容采用限行省略，避免撑坏布局；详情提供全文。具体限行数量待视觉验证，不能截断源数据。
- 点击卡片打开右侧宽面板，保留看板位置，支持展开完整页面。
- 面板顶部固定标题、状态、处理人和主要操作；主区展示原始报修、附件及按时间排列的补充、回复、处理记录。
- 右侧属性区展示报修人、位置、分类、责任、外部协助方、下次跟进时间。
- 输入区明确切换回复报修人/内部备注；新补充提示不覆盖正在输入的内容。
- “与我有关”包含本人负责处理、负责沟通或明确关注的工单。仅查看不自动加入；转交后若不再承担责任且未关注，不永久保留。
- 已关闭列默认显示北京时间今天及昨天关闭或解决的记录，并直接标明日期范围；按时间倒序分页加载，可切换日期或查看全部。待受理和处理中不因创建时间较早而隐藏。日期范围按 Asia/Shanghai 自然日计算，不使用滚动 48 小时或浏览器所在时区。
- 支持受控拖动：待受理到处理中执行“我来处理”；处理中到已关闭打开完工表单、提交成功后正式移动；已关闭到待受理要求重开原因。不适用移动明确提示，按钮入口始终保留。
- 首版列内采用自动排序，不保存人工拖动顺序：未跟进的新补充、到达跟进时间的事项优先，其余按等待时间；已关闭按完工时间倒序。拖动或操作期间实时更新的重排策略待交互验证，不能使操作目标突然跳走。

### 提醒体验

用户确认站内提醒并要求声音提醒：新报修更新待受理数量并突出卡片；与我有关的新补充、重开及跟进到期提供个人提醒数量和轻量提示，可直接打开工单。不抢焦点、不自动打开详情。浏览器桌面通知可选，由工作人员主动开启；后续 Tauri 沿用相同业务触发规则。

声音提醒纳入首版。交互细化建议：采用短提示音，提供静音及试听；同一事件跨标签页去重，短时间连续事件合并提示，不在断线恢复时逐条补响历史事件。声音触发范围、浏览器播放条件及设置呈现应在视觉/浏览器验证中落实；以上细化为工程建议，不能宣称当前已实现或所有浏览器可无交互播放。

## 9. 页面方案（待整体确认）

### 9.1 工作台外壳与首页

以 1920 × 1080 为主要设计画幅。建议侧栏 224px、顶栏 48px，内容区留白 24–32px；三列等宽、间距 16px，标题与工具栏保持紧凑。这些是初始视觉参数，不是不可调整的产品约束。

侧栏顶部显示工作区名称及全局搜索，中部显示已确认的六个导航项，底部放本人菜单、声音开关和连接状态。团队知识库呈现“规划中”的静态说明入口，不提供虚构文章或编辑按钮。

首页头部依次为“工作台”标题、团队工作/与我有关范围、看板/列表视图、搜索与筛选、新建报修。筛选建议支持处理人、故障类别、来源、细分状态、新补充和待跟进；日期筛选明确作用范围，已关闭列默认显示今天和昨天的实际日期。

全局搜索首版以编号、报修描述、授权范围内的报修人和位置为主；结果按对象标明工单或未建单受理。内部内容不能进入报修人搜索或对外结果。搜索当前不存在完整查询能力，需新增服务端契约，不能仅过滤已加载的部分卡片后宣称全量结果。

### 9.2 卡片与列表

卡片标题建议最多两行，位置与报修人一行，必要的状态/提醒一行，责任与时长一行；有下次跟进时间再显示对应信息。长文本省略但详情全文保留。附件只提示数量/类型，避免卡片载入大量媒体。

左上保留弱化编号，右上出现更多菜单；拖动手柄与正文点击区域区分。整卡点击打开详情，菜单、头像、文本选择不意外启动拖动。责任头像与实时协作头像分开，后者悬浮显示“某某正在查看/编辑”，断线或失活后不得持续声称正在操作。

待受理列可显示“待复核”“待接单”“已领取”“重开”等细分标签；处理中区分主动处理、等报修人、等厂商；已关闭中如存在 RESOLVED 记录，明确保留“已解决待确认”。新补充与已到跟进时间使用图标加文字，不能只依赖颜色。

列表与看板共享范围、筛选及同一批服务端事实。建议列为问题、状态、报修人/位置、处理人、当前环节时长、跟进时间、最新活动；点击打开同一个详情面板，不另造列表专用操作流程。

### 9.3 详情面板与人工复核

建议右侧面板宽 1040–1120px，上方固定问题标题、真实状态、当前责任和主动作；主体左侧为内容与活动记录，右侧约 260px 为属性区。窄窗口可展开为整页或折叠属性，不能挤压输入区。

未处理事项以“我来处理”为主动作，“先接单，稍后处理”“派给同事”进入次级操作。处理中以“完成并关闭”为主动作，等待报修人、联系厂商、转派及跟进时间靠近责任区；已关闭提供明确的重开入口。当前权限或状态不支持的操作不伪装成可执行按钮。

待复核材料在相同面板顶部显示“需要判断的原因”和必要缺失项，正文直接呈现已有报修资料。“我来处理”可完成合法的确认报修与开始处理复合动作，但无法判断是不是故障的材料仍需澄清；咨询、误报或范围外等归类保留简洁次级菜单，不把所有待复核内容强制建成故障。

活动流按时间串联用户补充、工作人员回复、内部记录、责任交接、状态动作及通知结果。内部记录始终标注内部；来源与受众清楚可辨。责任链单独提供可展开的“接单与交接记录”，便于直接追溯首次接单和后续转移。

详情停留在旧位置或正在输入时，新补充显示“有新补充”提示条，不抢焦点、不滚到底、不覆盖草稿；点击可跳到新内容。修改冲突保留输入并展示最新状态，禁止悄悄覆盖。

### 9.4 新建报修与完工表单

新建报修采用短表单：报修人选择/手填、科室与联系信息、位置或不清楚、故障描述、可选附件；默认不要求技术人员先填大量分类字段。底部“提交报修”与“由我处理”明确区分。展示真实代录来源及通知方式，身份未核实时提示需人工联系，不阻止保存诉求。

完工表单保留两个明确区域：必填内部处理过程、对外结果。对外内容建议提供模板式简短初稿供工作人员确认，不能擅自把内部处理记录全部复制。提交文案为“完成并关闭”，在一个授权事务中记录关闭事实；外发通过可靠通信异步处理。外发失败单独提示，关闭事实不撤销。

### 9.5 会话

会话页面向集中沟通：左侧会话列表，中间消息流与输入区，右侧关联报修/工单摘要。优先展示需要回应及与本人有关的会话，搜索与筛选保持范围可见。

从工单进入会话必须定位到对应服务主题；群内多人多故障不能汇成一个不分主题的操作窗口。来自网页且没有真实会话的事项仍在工单中处理，不显示虚构聊天内容或不可用发送按钮。

### 9.6 公共故障

采用列表与详情布局，顶部切换待确认、进行中、已恢复/关闭。列表显示故障名称、影响范围、关联报修数、负责人和持续时间。详情提供关联报修、处置记录与进展通知。

候选须人工确认；把个人报修关联到公共故障不删除原单。公共故障恢复后仍保留个人工单各自状态；不能用一键恢复同时冒充全部报修人故障已恢复。

### 9.7 通知异常、设置与知识库

通知异常以待处理列表呈现业务对象、接收渠道、失败/待核对状态和发生时间。详情提供安全的发送摘要与允许动作；群和个人两路结果分别展示，结果未知不提供盲目重发捷径。业务上的全员接管权不扩大通知核对权限。

设置首版优先呈现个人声音开关/试听、桌面通知开关及个人偏好。系统配置仅展示实际已有且获准开放的项；不从“设置”扩展出新的全院人员、组织、权限或规则管理平台。

团队知识库只显示规划中说明。文章结构、权限、检索、审核和与工单的关联留待专门设计，不阻塞管理端首版。

## 10. 视觉与交互基准（建议）

| 项目 | 初始建议 |
| --- | --- |
| 工作区/侧栏 | 白色工作区、近中性的浅灰侧栏 |
| 排版 | 系统中文无衬线字体；正文 14px，辅助 12–13px，页标题约 24px |
| 卡片 | 轻边框、8px 左右圆角；仅悬浮/拖动/面板需要适度阴影 |
| 状态色 | 待受理浅暖色、处理中浅蓝、已关闭浅绿；文字仍表达真实状态 |
| 动效 | 通常 120–200ms，突出跟手和反馈；减少动态偏好下简化过渡 |
| 键盘 | 可见焦点、Esc 关闭可退出浮层、按钮可替代拖动；输入有内容时不无声丢弃 |

自动排序不意味着实时抢位置：拖动或鼠标操作期间保留操作目标，暂缓受影响列表重排并提示有更新；放手后按最新服务端状态恢复排序。拖动期间不等待网络才跟随指针，落点需要表单时先完成表单，提交成功才改变业务归属列。取消恢复原位置，冲突刷新真实状态并保留输入。

声音短促、可静音、可试听；同一浏览器多标签去重，同一时间簇合并提醒。新报修及与本人有关的新补充/重开/跟进到期作为首版建议声音事件，不把整个团队所有后台变更都播放成声音。浏览器未允许播放时明确呈现启用入口，仍提供视觉提醒。

空列表区分确实没有事项与筛选无结果；加载采用稳定占位，避免整页闪烁；断线显示状态并补取数据，不能继续显示虚假的“实时”。无法确认提交结果时通过原命令恢复核对，不引导用户重复创建新操作。不同窗口尺寸至少保证查看、输入和主要动作可用。

## 11. 实施分界与体验验收（待整体确认）

先建立带合成数据的管理端视觉原型，验证看板、详情、新建、关闭及拖动；再按现有 API 与新增契约分别接入。界面原型通过不等于真实业务闭环或现场验收。当前讨论未开始框架迁移、部署或外发。

需要新增或修订的能力包括：聚合看板与搜索、复核/接单/开始处理的复合命令、直接完工关闭、相互接管及责任链查询、成员选择与代录、个人未读及补充待跟进、预约跟进、短暂协作状态、本人未解决反馈及重开、按来源可靠通知。复用现有工单事实源、认证、版本控制、幂等及 SSE，不把界面状态变成新的业务权威。

验收场景：

1. 从待受理卡片一次“我来处理”完成合法承接和开始处理，不切换页面逐项确认。
2. 张三转给李四，界面显示李四负责，首次接单及交接链均可追溯。
3. 写内部记录期间到达新补充，输入保留且有提示；旧操作不能清除新补充待跟进。
4. 两人同时接管/关闭，只有合法版本提交成功，另一人获得明确提示且输入不丢。
5. 完工内部过程不外发；报修人从本人详情点击仍未解决，只重开同一工单一次。
6. 已关闭列仅默认展示北京时间今天/昨天，历史仍能查询，未完事项不按日期隐藏。
7. 开关声音、重复 SSE、多标签与断线恢复均不产生重复连续鸣响。
8. 卡片长文本不破坏布局；拖动与菜单、输入、滚动、SSE 更新协同，实际负载下无明显卡顿。
9. 成员目录不可用仍能手工代录，身份待核实时不向猜测对象发送通知。

具体颜色、组件尺寸及拖动实现可在视觉原型中调整；超时规则、知识库功能及 Tauri 原生能力按已明确范围另行处理。
