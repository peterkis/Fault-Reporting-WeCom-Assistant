# 32. 企业微信全局错误码引用与排障规范

- 状态：ACTIVE（规范更新；不改变 Gate、P1-012 或任何验收状态）
- 适用范围：WeCom Adapter 的长连接、回调回复、主动投递、模板卡片、临时素材上传/下载，以及其后的 Delivery 排障。
- 权威外部来源：企业微信[全局错误码（90313）](https://developer.work.weixin.qq.com/document/path/90313)。本项目于 2026-08-29 核对；该页自身标注最后更新为 2026-08-13。
- 相关规范：[WebSocket 接入](07_wecom_websocket_integration.md)、[临时素材约束](18_wecom_temporary_media_constraints.md)、[测试与验收](13_test_acceptance_plan.md)、[运维 Runbook](15_deployment_operations_runbook.md)、[P1-002 Adapter](21_p1_wecom_sdk_adapter.md)、[P1-007 Outbox](26_p1_notification_outbox.md)。

## 1. 权威性与基本原则

90313 是动态的官方目录，不在仓库复制完整错误码表；排障时先查该页面，再查对应命令的接口文档和当前锁定 SDK 行为。本文只保留本项目已涉及的高频代码、稳定记录格式和处置规则。

企业微信明确要求以数值 `errcode` 判断结果，不能依赖可调整的 `errmsg`。因此：

- 程序分支、告警聚合和回归断言只使用 `errcode`、操作上下文和项目稳定错误码；
- `errmsg` 只可在受控的本地即时诊断中查看，不能成为契约、日志、指标、证据或工单字段；
- `errcode=0` 只说明提供方接受本次请求。它不证明被动回复或主动投递已在企业微信客户端显示、打开或播放；客户端观察仍是独立证据；
- 未返回 `errcode` 的连接异常、SDK 超时或进程中断保持为 `UNKNOWN`，不得伪装为某个提供方错误码，也不得据此盲目重复投递。

## 2. 统一错误记录与映射边界

每次可观测的企业微信调用至少关联下列脱敏字段；`provider_errcode` 缺失时明确记录为 `null`，而不是猜测数值。

| 字段 | 规则 |
| --- | --- |
| `operation` | 枚举调用边界，例如 `subscribe`、`respond_msg`、`send_msg`、`upload_init`、`upload_chunk`、`upload_finish`、`download_media` 或 `card_update`。 |
| `provider_errcode` | 企业微信实际返回的整数，或 `null`。保留原值，不能只留下翻译后的文字。 |
| `internal_error_code` | 项目的稳定 `WECOM_*` 分类；它服务于跨 SDK/网络条件的告警与业务降级，不能假定与提供方代码一一对应。 |
| `outcome` | `ACKED`、`REJECTED` 或 `UNKNOWN`。超时、断线和未获得回执均为 `UNKNOWN`。 |
| `retry_class` | `NONE`、`BOUNDED`、`WAIT_FOR_WINDOW`、`REBUILD_INPUT`、`REACQUIRE_CONTEXT` 或 `MANUAL_REVIEW`。 |
| `trace_id` / `outbox_id` | 仅保留项目侧关联标识；对通道会话只使用受控哈希，不写原始 `req_id`、`upload_id` 或 `media_id`。 |

内部稳定码（如 `WECOM_SEND_TIMEOUT`、`WECOM_MEDIA_SIZE_EXCEEDED`、`WECOM_CARD_EXPIRED`）不得覆盖原始 `provider_errcode`。相反，记录应同时保留两者：前者描述项目如何处理，后者支持按官方目录定位提供方原因。P1-002 的纯入站 Frame 转换目前不调用企业微信服务端命令，因此它只返回已冻结的本地 `WECOM_INVALID_FRAME`/`WECOM_UNSUPPORTED_MESSAGE_TYPE`；不得把不存在的提供方代码伪造进该结果。

## 3. 项目相关官方代码速查

下表是 2026-08-29 从 90313 核对的最小运行集，不替代官方全表或具体接口的额外限制。

| `errcode` | 官方含义（简写） | 项目处理 |
| ---: | --- | --- |
| `0` | 请求成功 | 记录 `ACKED`；媒体/消息仍按回复侧或主动侧分别保留客户端可见性证据。 |
| `-1` | 系统繁忙 | 仅对幂等且回执明确为失败的操作退避重试，最多 3 次；否则按 `UNKNOWN` 进入对账。 |
| `40004` | 不合法的媒体文件类型 | 本地格式、Magic、MIME 与目标命令类型校验失败；修复输入后重新创建受控上传流程，不原样重试。 |
| `40005` | 不合法的 `type` 参数 | 修复 Adapter 类型映射；不以 `file` 伪装 `voice`/`video`。 |
| `40006` | 不合法的文件大小 | 失败关闭；不能静默转码、压缩或改用公开链接。 |
| `40007` | 不合法的 `media_id` 参数 | 不能把该租约当作可重用投递凭据；核对类型、机器人归属和有效期后按受控路径重新上传。 |
| `40008` | 不合法的 `msgtype` 参数 | 修复消息体/回复命令契约，不把一次群内 @ 或 SDK 行为概括为通用平台能力。 |
| `40011` | 上传视频大小不是有效值 | 失败关闭并按媒体大小约束处理；不以 SDK 分片能力绕过提供方上限。 |
| `40145` | `mediaid` 已过期失效 | 标为 `WECOM_MEDIA_LEASE_EXPIRED`，从受控源重新上传；不得重用过期标识。 |
| `42045` | `Template_Card.card_action` 缺失或不合法 | 标为参数/卡片契约错误；不重放点击，也不将事件 Frame 当普通消息。 |
| `45009` | 接口调用超过限制 | 标为 `WECOM_MEDIA_RATE_LIMITED` 或对应发送限流；等待本地配额窗口，禁止忙等和绕过限流。 |
| `93006` | 不合法的群 ID | 标为目标配置错误；校验目标和会话类型后人工修正，不能对原目标自动重试。 |
| `846604` | `req_id` 已过期 | 标为 `WECOM_CARD_EXPIRED` 或回调上下文已失效；不得把过期被动回复自动升级为主动推送。 |
| `846605` | 不合法的 `req_id` | 标为回调绑定/命令契约错误；核对当前事件上下文，不能用其他消息的 `req_id` 替代。 |

`846604`/`846605` 的最终内部分类取决于操作上下文；它们不是“可换一个 `req_id` 后继续发送”的通用重试信号。现有 Gate 0 对空反馈响应、过期卡片和群内被动回复的观察仍只证明各自场景，不扩展为未验证能力。

## 4. 重试、幂等与投递纪律

1. 先判定操作是否已经具有提供方回执；有 `errcode=0` 时禁止同一 Delivery 直接再发。
2. 对 `-1`，仅在幂等、输入仍有效且上次明确被拒绝的前提下执行有界退避；官方建议重试次数不超过 3 次。
3. 对 `45009`，以本地限流器和持久化 Delivery 窗口为准，等待下一允许窗口；不得通过增加并发或更换进程规避限制。
4. 对参数、格式、大小、目标和卡片契约错误，分类为 `REBUILD_INPUT` 或 `MANUAL_REVIEW`，而非网络重试。
5. 对过期媒体租约，只能重新上传经授权的受控原始素材；对过期/非法回调 `req_id`，当前被动回复流程结束。是否另行通知由已授权的业务规则和 Outbox 决定，不能由 Adapter 自动越权转换。
6. 对超时、断线或 SDK 异常，先记录 `UNKNOWN` 和稳定内部码，按 Delivery 幂等键、项目侧审计和必要的客户端观察对账；不能把未确认请求视作失败后盲目重发。

被动回复与主动投递的幂等、时限和用户可见性各自独立。一个路径的 `errcode=0`、SDK ACK 或客户端显示，不能替代另一条路径的验收。

## 5. 安全记录与证据

允许写入普通日志、指标固定标签或脱敏证据的仅包括：操作枚举、`provider_errcode`、稳定内部码、结果类别、尝试序号、耗时、SDK 版本、连接代次、`trace_id`、哈希化的会话/目标标识和无敏感的人工处置结果。

禁止写入：`errmsg`、Bot Secret、原始 `req_id`、`upload_id`、`media_id`、媒体 URL、AES Key、原始消息/转写、文件名、Base64、媒体字节、群/用户原始 ID。需要请求关联时使用项目 `trace_id` 或受控哈希；如确需向提供方支持渠道提交原始诊断数据，必须走独立授权与最小化披露流程，不能从普通日志复制。

## 6. 测试与更新规则

- 单元与 Contract Test 覆盖 `errcode → internal_error_code/retry_class/outcome` 的确定性映射、缺失 `errcode` 的 `UNKNOWN`、`errmsg` 不参与分支，以及脱敏字段白名单；
- 媒体测试覆盖 `40004`–`40007`、`40011`、`40145` 与 `45009` 的本地失败关闭、重新上传/等待窗口纪律；
- 回调和卡片测试覆盖 `42045`、`846604`、`846605` 的当前上下文校验，禁止跨消息复用 `req_id`；
- 真实租户或客户端结论必须单独记录，不能由错误码映射测试、Mock 或 ACK 替代；
- 发现新代码时，记录操作上下文、数值、稳定分类和最小脱敏证据，先核对 90313 与具体接口文档，再更新本文件和测试；不得根据 `errmsg` 或单次 SDK 异常臆测官方含义。

本规范不授权新增企业微信调用、扩大主动投递、变更重试次数，或推进任何阶段任务；它只为现有及后续获批实现提供可审计的排障约束。
