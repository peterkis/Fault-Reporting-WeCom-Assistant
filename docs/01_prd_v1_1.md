# 01. 产品需求文档 PRD V1.1

## 1. 文档信息

| 属性 | 内容 |
|---|---|
| 产品名称 | 医院信息故障智能报修助手 |
| 对外名称 | 信息保障助手（暂定） |
| 版本 | V1.1 Agent 开发基线 |
| 目标读者 | 信息科管理层、产品、开发、测试、企微管理员、安全合规人员 |
| 当前阶段 | Gate 0：企业微信能力验证 |
| 保密级别 | 院内 |

## 2. 产品愿景

让临床人员在熟悉的企业微信入口中完成报修，并清楚知道：

1. 系统已经可靠收到；
2. 工单已经生成；
3. 是否有人接单；
4. 当前处理到哪一步；
5. 是否需要补充信息；
6. 何时处理完成；
7. 问题未恢复时如何重新打开。

信息科能够获得可统计、可审计的服务数据，同时保留人工控制权。

## 3. 核心目标与指标

| 目标 | 口径 | V1目标 |
|---|---|---:|
| 首次确认 | 数据库事务提交至企业微信确认接受回复 | P95 ≤ 3 秒，P99 ≤ 8 秒 |
| 工单创建 | 消息接收至 Tickets 创建成功 | P95 ≤ 5 秒，P99 ≤ 10 秒 |
| 明确报修漏单 | 明确发给机器人但未形成 Intake 或人工待办 | 0 |
| 重复建单 | 同一 `provider + msg_id` 生成多张工单 | 0 |
| 状态通知 | 工单状态事务提交至企业微信接受消息 | P95 ≤ 10 秒 |
| 核心链路可用性 | WebSocket 接入、PostgreSQL、Tickets、Outbox | ≥ 99.9% |
| AI 降级 | AI/OCR 停止后仍可建单和通知 | 100% |
| 可追溯性 | 消息→Intake→Ticket/Incident→Notification | 100% |
| 敏感数据日志泄漏 | 患者数据进入普通日志 | 0 |
| 自动公共事件关联 | 达到精确率门槛前只提示候选 | 默认关闭 |

## 4. 用户角色

### 4.1 临床医生和护士

核心诉求：

- 不改变主要沟通习惯；
- 报修后快速获得工单号；
- 不用反复在群里追问；
- 能补充截图、位置和终端编号；
- 能确认是否恢复。

### 4.2 信息科工程师

核心诉求：

- 自动形成待处理任务；
- 能在手机或现有工作台接单；
- 查看原始描述、截图和上下文；
- 快速请求补充信息；
- 清晰记录处理结果；
- 不在多个群之间反复沟通。

### 4.3 值班管理员

核心诉求：

- 处理未映射身份、低确定性分类和公共故障候选；
- 维护值班和处理组；
- 查看超时、积压和服务指标；
- 在 AI 失败时接管分诊。

### 4.4 系统管理员与安全人员

核心诉求：

- 管理企业微信机器人配置；
- 审计连接、权限、消息处理和附件访问；
- 控制留存、脱敏和密钥；
- 完成故障演练和合规检查。

## 5. 核心用户故事

### US-01：群内文字报修

医生发送：

```text
@信息保障助手
本部 3 楼护士站 HIS 登录报错
```

系统应：

1. 接收并持久化消息；
2. 创建 Service Intake；
3. 调用现有 Tickets 创建工单；
4. 回复工单号和“等待受理”；
5. 异步识别系统、模块、错误类型和处理组。

### US-02：图文报修

医生发送文字和截图。系统应：

- 保存文字和图片关联；
- 先创建工单；
- 异步 OCR；
- 提取错误代码和界面标题；
- 更新工单结构化字段；
- AI/OCR 失败不影响工单。

### US-03：纯图片报修

医生只发截图。系统应：

- 创建 Service Intake；
- 创建“等待补充说明”的工单；
- 回复工单号；
- 请求补充一句故障现象；
- OCR 结果可作为辅助，不得因无文字而丢弃。

### US-04：工程师接单和处理

工程师在 Hub、灵动岛或 H5：

- 查看待处理工单；
- 点击接单；
- 点击开始处理；
- 填写对外可见或仅内部可见备注；
- 请求补充信息；
- 完成解决。

### US-05：申报人补充信息

工程师请求终端编号后，申报人通过机器人卡片或 H5 补充：

- 文字；
- 终端编号；
- 图片；
- 发生位置。

系统将补充内容追加到同一个 Intake 和 Ticket，不新建工单。

### US-06：解决确认和重开

工单解决后，申报人收到单聊卡片：

- `已恢复`：关闭工单；
- `仍未恢复`：重新打开并回到原处理队列；
- 超时自动关闭前应提醒，并记录关闭原因。

### US-07：公共故障

多个科室报告同一错误特征：

- 保留每次独立 Intake；
- 生成 Incident 候选；
- 管理员确认关联；
- 群内发布统一公共故障公告；
- 所有申报人收到后续重要进展；
- 不重复生成大量相同处理任务。

### US-08：AI 服务停止

管理员停止 AI/OCR 服务后：

- 机器人仍能接收消息；
- 仍能创建工单；
- 仍能回复工单号；
- 工单进入人工分诊；
- 系统产生 AI 降级告警。

## 6. 功能范围

### 6.1 P0：可靠受理和工单闭环

- WebSocket 连接、认证、心跳、重连；
- 文本、图片、mixed 等能力 PoC；
- 消息标准化和 `msg_id` 幂等；
- Channel Message 和 Service Intake；
- 现有 Tickets 创建；
- 工单状态机；
- 首次确认；
- 单聊状态通知；
- Outbox/Delivery；
- 身份、院区、科室最小映射；
- 工程师 H5；
- 监控、日志、审计和降级。

### 6.2 P1：媒体、AI 和公共故障候选

- MinIO 私有附件；
- OCR；
- 规则和系统指纹；
- 小模型影子分类；
- 人工修正页面；
- 模板卡片；
- 补充信息；
- Incident 候选；
- 多申报人订阅；
- 月度指标。

### 6.3 P2：运营增强

- 经评估后启用高确定性自动路由；
- 监控告警和 API 平台信号关联；
- 历史相似工单；
- 故障知识库；
- 服务目录扩展；
- 扩展至装备、后勤等服务域。

## 7. 业务规则摘要

1. 明确发给机器人即形成 Intake。
2. 明确故障报修立即创建工单，不等待 AI。
3. 无法判断是否故障时，形成 Intake 并请求澄清，不静默丢弃。
4. 同一用户 90 秒内的补充消息默认追加到当前 Intake。
5. 工单状态只有实际接单后才能显示“已受理”。
6. 只有实际开始操作后才能显示“处理中”。
7. 公共故障使用 Incident 关联，不删除个人申报。
8. 内部备注和外部可见说明必须分开。
9. 处理照片是否必填由服务目录配置。
10. 自动关闭与用户确认关闭必须分别统计。

## 8. 通知策略

- 首次工单号：群内回复，必要时同时单聊；
- 已接单：单聊；
- 开始处理：单聊；
- 待补充：单聊并提供操作入口；
- 已处理待确认：单聊卡片；
- 公共故障确认和重要进展：群内 + 订阅人单聊；
- 内部处理日志：不对临床发送。

## 9. 数据原则

- 原始消息不可被 AI 结果覆盖；
- AI 结果必须记录模型、规则和 Prompt 版本；
- 人工修正保留前后值；
- 附件设置敏感级别和留存到期时间；
- 未形成服务请求的简单问候短期留存后删除；
- 禁止用真实患者消息直接作为模型训练集。

## 10. 上线策略

1. Gate 0 能力验证；
2. 信息科内部测试群；
3. 一个合作良好的临床试点群；
4. AI 仅影子运行；
5. 通过指标门槛后扩大范围；
6. 每个阶段支持回滚至“人工分诊 + 正常建单”。

## 11. Go/No-Go 条件

### Gate 0 通过条件

- WebSocket 连续运行 24 小时；
- 群/单聊文本能力确认；
- 图片或 mixed 实际行为确认；
- 主动向用户和群推送能力确认；
- 卡片按钮事件确认；
- 断网恢复和消息幂等验证。

### V1 试点通过条件

- 明确报修漏单为 0；
- 同一消息重复建单为 0；
- AI 关闭仍可建单；
- 状态语义无虚假；
- 截图不进入公开日志；
- 群内通知量可接受；
- 临床可完成解决确认和重开。
